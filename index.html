報告摘要

本報告匯總了近期針對 Dify AI、OpenRouter、Coze（扣子）國際版及前端託管看板 的深度技術對話。核心目的在於解決雲端 RAG 平台之 50MB 免費儲存容量限制，並在確保「父子分段（Parent-Child）」與「重排（Rerank）」等高級檢索精準度的前提下，將 OpenRouter API 成本鎖定在每句話 $0.01 美元以內。

💰 GPT-5.6 Luna 單次對話 $0.01 美元卡價公式：

在 OpenRouter 中，Luna 的輸入為 $0.20/1M，輸出為 $1.20/1M。若要將單次點擊成本壓在 $0.01 USD 以內，後台總輸入上限必須控制在 48,200 Tokens 內。配合 Dify/Coze 限制 Top K = 3 與限制對話歷史（Window Size = 10~15），實際單次成本僅約 $0.002 ~ $0.005 美元，極度安全。

2 Dify 50MB 封印解除與 RAG 三大支柱

一份 225.6k 字元（約 22.5 萬字）的 Word 調查報告，原始大小僅 233KB。但在 Dify 的「高品質索引 + 父子分段 (4000/900)」下，因為高維度矩陣指針複製，會在後台膨脹成 46.5 MB 的巨量向量數據，直接觸發官方 50MB 免費額度爆滿的大紅線警告。

📚 RAG 系統

整座圖書館的翻書、核對、交給 AI 閱讀並回答的完整系統運作流程。

🔍 Embedding (嵌入)

第一階段搜尋。將問題與 Chunk 轉為數字向量，0.01 秒大範圍粗篩出 20 條資料。

⚖️ Rerank (重排)

高級圖書管理員。地毯式人工審查粗篩結果，給出精準打分排序，抓出前 3 條（Top K=3）。

🚨 關於 Dify 刪除檔案空間不釋放的真相：

Dify 雲端版點擊「刪除」屬於邏輯刪除（Soft Delete），檔案會進入暫存快取區。由於免費版異步清理任務（Garbage Collection）伺服器排隊嚴重，常需 24-48 小時才會物理刷盤。唯一免等待的暴力破解法為：更換新帳號 或 在本地用 Docker 自建開源版 Dify 徹底解除 50MB 封印。

3 轉戰 Coze (扣子) 的參數還原與限制

為了解決容量問題，我們嘗試將陣地移往字節跳動旗下的 Coze 國際版 / 國內企業版。Coze 免費版提供數 GB 的永久儲存，但由於免費個人版閹割了「Hierarchical（層級父子分段）」功能，我們在 Custom（自訂分段） 中採用了「隱藏父子模式」的黃金替代參數：

  • • Segment ID (分隔符): Line break (\n)
  • • Maximum segment length (最大長度): 3,500 characters
  • • Segmentation Overlap Degree (重疊比例): 25 % (等同 ~875字重複)
  • • Text Preprocessing (文字預處理): 取消勾選第一個連續換行擦除開關

透過 3500 字的大區塊與 25% 的高密度鏈條重疊，我們成功在 Coze 的單層扁平資料庫裡，還原了 Dify 父子模式下前後因果脈絡不被切斷的檢索強度。

4 內部調查報告與管理層匯報專用 Prompt

以下是專為第二個知識庫（Investigation Report & Management Communication）獨立工作流編寫的 LLM 節點終極提示詞。該提示詞嚴格遵循「無視無關變量、全量最大化提取、禁止廢話草稿以控管 Token」之鐵律： 

# 角色
你是一個精通國際郵務內部營運、懂得舉一反三的【內部調查與管理層匯報比對助手】。

# 核心常識
在國際郵務內部管理中，不論具體涉及的是哪一個國家、哪一個單號或哪一個時間點，針對運務異常、遺失、延誤或系統性錯誤的【內部調查思路（Investigation Report）】與【對上級管理層的匯報口徑（Management Communication）】，其責任歸屬判定與溝通邏輯是完全通用的。

# 檢索到的知識庫內容
{{#context#}}

# 任務
請讀取用戶輸入的新異常案件或調查需求。當你比對知識庫時，【請無視具體的單號、日期或涉及的國家差異】。只要「事故成因（Root Cause）」、「內部調查切入點」或「對管理層的匯報口徑」相同，即屬於高度相似案例。

# 輸出邏輯與格式
1. 開頭請統一使用這句話：「Boss，針對這次的內部調查與匯報，我幫你找到了處理邏輯一模一樣的通用舊案例，你可以參考它們的調查與報告邏輯：」

2. 【案例數量強制要求】：
   - 絕對禁止只列出 1 2 個案例！只要上下文（Context）中有相關的案例，**必須「全部、毫無遺漏地」通通列出來（N 個相關就必須列出 N 個）**，按最相似到次相似排列。

3. 每個案例請按以下格式列出（絕對不需要生成任何完整的報告草稿 Draft 或結論）：
   - **案例 [編號]：（事故類型 / 匯報對象）**
   - **報告識別 / 主題：** [列出原文的報告名稱、調查單號；若原文未記載，請寫「【識別：原文未記載】」並附上該報告內容前 30 個字以供檢索]
   - **相似原因：** [簡述是「事故起因/異常特徵相似」，還是「對管理層的處置與匯報口徑合適」]
